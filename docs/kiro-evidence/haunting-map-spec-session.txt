Create a new spec named `haunting-map` in .kiro/specs/haunting-map/: write requirements.md, design.md and tasks.md (no code in this session). Follow the format of .kiro/specs/ward-hardening/ and .kiro/specs/first-seance/ (Why, Scope, numbered EARS-style requirements, non-functional, Out of scope; design with real files, exact signatures, copy text, element ids, correctness properties for fast-check; tasks test-first, each task leaving npm test / typecheck / lint / contrast green, a traceability table, nothing ticked).

What it is: after a summon, the page shows "The haunting map": which files of the repository are haunted by which departed author. It answers a question a maintainer actually has: where does the knowledge live only with people who have left? It is computed deterministically from git history. No model call, no invented number: every figure on the map is a count of commits, and every tile names the commit it rests on.

Decisions already made (write them as requirements, reasoning in "Why"):
A. Data source: one `git log --name-only` call over the history that was read (no blob downloads, so it works on the blob-less clone; no --numstat, no per-file blame), capped at 2,000 commits and 10 s, and one `git ls-tree -r --name-only HEAD` for the files that exist now. It runs inside the summon while the clone still exists, and must not delay or fail the summon: if it fails or times out, the summon succeeds and the map is absent with a plain reason.
B. Definitions, all relative to the repository, never to the wall clock (so the same repository state always gives the same map):
   - `repoNow` = the newest author date in the history read.
   - an author is identified by name + email (lower-cased email); display uses the name.
   - an author is "departed" when their latest commit in the history read is more than `DEPARTED_AFTER_DAYS` (365) before `repoNow`.
   - for a file that exists at HEAD, `touches(author)` = number of commits by that author that changed the file (renames are not followed; say so).
   - the file is "haunted by" the departed author with the most touches; ties go to the one who touched it most recently, then to the name in code-unit order. A file no departed author touched is "tended by the living".
   - `share` = touches by departed authors / all touches, shown as "N of M commits".
   - each haunted file carries the ghost's last commit to it: sha7 and date ("last seen").
   - merge commits are skipped; paths are capped at 300 files (largest share first, then path order) and the response says when it was cut; binary or vendored paths are not special-cased (say so).
C. API: the summon response gains `map?: { repoNow, departedAfterDays, commitsRead, truncated, ghosts: [{ name, lastSeen, files }], files: [{ path, hauntedBy: string | null, departedTouches, totalTouches, lastSha7, lastSeen }] }` validated by a Zod schema, plus `mapNote?: string` when the map is absent. A pure function `computeHauntingMap(commits, headFiles, opts)` holds all the logic (property-tested); a thin git reader feeds it.
D. UI: a section "The haunting map" between the séance and the exorcism, shown after a summon when a map exists. A legend lists each ghost (name, "last seen <date>", number of files) with a text glyph made from the initials (not colour alone). Files are tiles grouped by ghost, then "Tended by the living" last and collapsed by default. Each tile: path (monospace, wraps), "Haunted by <name>", "N of M commits", "last seen <date>", the sha7, and a button "Summon here". The currently summoned file's tile is marked with text ("You are here"). Fog-like intensity may follow `share` but only as a second signal next to the text. Reduced motion respected; no new animation beyond an opacity transition. It must work at 320 px without horizontal scroll and be fully keyboard operable (tiles are not focusable themselves; the button is).
E. "Summon here": the page calls /api/summon for that file with `wholeFile: true` instead of line numbers; the server reads the file's length at HEAD (one git call) and uses lines 1 to min(length, 500), returning the range it used. The ghost of that file can then be asked as usual. An empty or missing file returns the normal 4xx with a plain sentence.
F. Samples: the crypt already has four authors over five years; state in the design the exact expected map for the crypt and for the possessed repo (compute it from the scripts' fixed dates), and test it against real git. If the crypt gives a dull map, add at most two commits to scripts/make-crypt.sh ONLY IF that does not change the ledger for legacy/tax.js line 7 (the recorded fixtures are keyed by that ledger; changing any existing commit's hash would invalidate them, so new commits may only be appended at the end, and you must show that the fixture prompt hashes stay the same). Prefer not touching the crypt.
G. Hostile repositories: author names and paths are untrusted text (textContent only; the map never goes into a model prompt). An author flagged by the existing isSuspicious needle check on their name is shown with the existing warning label wording.
H. Tests: unit and property tests for computeHauntingMap (shares in [0,1]; departedTouches <= totalTouches; every hauntedBy is a departed author who touched the file; determinism under input shuffling; adding a commit by a living author never increases a file's share; cap and truncation flag), real-git tests on both samples, server tests (map present, map failure does not fail the summon, wholeFile), and a jsdom end-to-end flow in test/e2e/ (summon -> map renders -> "Summon here" on another file -> crypt and line view change).
I. Out of scope: line-level ownership (blame), following renames, time-travel views, per-directory roll-ups, any model use.

Constraints: follow .kiro/steering/ui-spooky.md (tokens only, new text/background pairs added to the contrast table and passing npm run contrast, no colour-only signalling, no emoji icons, labels in sentence case); CSP default-src 'self' (no inline styles in HTML; element.style from JS is allowed as the existing bars do); no new dependency; verifier.ts and the rate limiters are not touched; the summon limiter applies to "Summon here" like any summon.
Write the three files and nothing else.

Extra context: another Kiro session is editing public/ right now for accessibility fixes (field error wiring, a "Still the candles" toggle, ledger rows as tabindex -1, forced-colors block). Design against the structure you see (the guide, #source, .seance-col, the e2e harness in test/e2e/harness.ts), and do not depend on exact line numbers. Recorded answers (recordings/) and fixtures are keyed by the crypt and possessed ledgers and prompts: nothing in this spec may change the samples' existing commits, the prompts, or the verifier.
